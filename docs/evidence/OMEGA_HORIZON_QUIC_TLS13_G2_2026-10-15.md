## Библиотеки, ключи и идентичность

Вместо первоначально выданного обоим узлам общего 32-байтного PSK используется **aioquic 1.6.1**, стандартный QUIC с TLS 1.3, и **cryptography 46.0.4**. Сервер создаёт временный сертификат, подписанный исключительно лабораторным CA. Клиент **сначала** проверяет цепочку доверия и DNS-имя omega-peer через библиотеку, **затем** дополнительно сверяет SHA-256 отпечаток точного leaf-сертификата, и **только после этого** передаёт синтетическую QUIC DATAGRAM.

Фиксация leaf-сертификата использует **внутренний, не публичный API aioquic**: это допустимо только для исследовательского стенда, **не production pin implementation**. В CI есть отдельный случай, когда мошеннический сервер предъявляет другое удостоверение **с тем же именем и от того же тестового CA**. Цепочка при этом корректна, но **проверка pin отклоняет сервер**. Нет собственной криптографической реализации TLS или QUIC. Сессионные ключи согласуются QUIC/TLS вместо заранее распространяемого общего симметричного ключа. В тесте не используются session tickets и 0-RTT.

**Важнейшее ограничение:** проверяется только сервер! **Никакой проверки личности клиента сервером ещё нет**. Подключение злоумышленника с доступом к QUIC endpoint как клиента здесь возможно. Для production нужна стандартная взаимная аутентификация/авторизация, а не самодельный handshake.

## Матрица восьми сценариев

| Сценарий | Фактически наблюдавшийся результат |
| --- | --- |
| Direct QUIC/TLS через явно настроенное перенаправление порта NAT | PASS, QUIC DATAGRAM и pinned leaf |
| Peer без входящего порта → исходящая регистрация → blind relay | PASS, QUIC DATAGRAM и pinned leaf |
| Неправильное DNS-имя сертификата, подписанного лабораторным CA | TLS отказ, application DATAGRAM не послан |
| Подмена leaf-сертификата с правильным DNS и тем же CA | PIN_REJECTED, application DATAGRAM не послан |
| Relay повреждает QUIC handshake | Соединение не устанавливается, application DATAGRAM не послан |
| Два отдельных QUIC-соединения к тому же peer | Оба PASS, разные QUIC Connection IDs |
| Новый QUIC-сеанс после перезапуска peer с прежним тестовым nonce | Повтор отвергнут SQLite-journal, новый nonce принят |
| Нет прямого входящего пути и relay не запущен | HANDSHAKE_OR_PATH_FAILED, application DATAGRAM не послан |

При обычном relay сценарии он перенаправил **4039 байт** сетевых данных, не имея ключей и не наблюдая тестовый plaintext marker. Это подтверждает ограниченный наблюдаемый факт, **не криптографическое доказательство абсолютной конфиденциальности**.

## Воспроизведение

Из исследовательской ветки на одноразовом изолированном Ubuntu GitHub runner (Python 3.13, sudo, iproute2, iptables, OpenSSL):

~~~bash
python3 -m pip install 'aioquic==1.6.1' 'cryptography==46.0.4'
sudo -E "$(command -v python3)" research/horizon/quic_netns.py --orchestrate
~~~

Программные сертификаты и ключи генерируются **только на время запуска** во временной директории. Не коммитить сертификаты, ключи, IP третьих лиц или telemetry о реальных посещённых сайтах.

## Оставшиеся уязвимости и приоритеты

1. **У сервера отсутствует аутентификация клиента.** Разработать проверенную схему mutual authentication на поддерживаемых публичных API, лучше через зрелую QUIC/TLS реализацию с mTLS и закреплёнными идентичностями. Избегать неофициальных private API для production.
2. **Нельзя безопасно распределять pin и доверие пользователям автоматически.** Сертификат/pin лабораторно доставляется обоим участникам заранее через общую локальную директорию. Нужны verified enrollment и отзыв/ротация идентичности, угроза Sybil/eclipsing, защита каталога от подмены.
3. **Повтор после перезапуска** отклоняется маленьким локальным SQLite журналом *синтетических сообщений*. Это не глобальная/переносимая anti-replay архитектура, не тест после полного перезапуска устройства и не защита при компрометации хранилища.
4. **QUIC/TLS 1.3 предоставляет стандартный механизм согласования сессионных ключей**, но лаборатория не проверяла формально forward secrecy или post-compromise security. Не заявлять такие гарантии без специализированного review.
5. **В relay отсутствует полноценная аутентификация и защита от ресурсного истощения**: он просто пересылает QUIC ciphertext. Он может наблюдать IP, объёмы, метаданные времени, отказывать в услуге.
6. **Нет UDP hole punching через реальные CGNAT**, мобильного Android ARM64, TUN, DNS/IPv6 leak capture, интернета через добровольный exit, отсутствия DPI fingerprint и защищённости от РКН. Direct соединение в тесте требовало явного NAT port forward. Нет никакой гарантии абсолютной анонимности.

**Гейт G2: PARTIAL**. Предпочтительное направление R&D: поддерживаемая QUIC/TLS реализация с взаимной аутентификацией и проверенными ACL/identity, без самодельного криптографического протокола. Основной Android Xray в main, M2/M5 и release gates **не изменены**.
